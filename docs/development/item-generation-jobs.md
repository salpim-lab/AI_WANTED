# 아이템 생성 작업 설계

2026-09-18 업데이트. 정상 생성은 상담 기반 아이템을 사용하고, 대체 아이템은 생성 실패 때만 지급한다. 작업 상태용 마이그레이션 `20260917110000_1070_item_generation_jobs.sql`을 추가했다. `item_candidates`는 2026-09-17에 이 테이블로 대체되어 마이그레이션(1025·9020)을 삭제했다. `candidate_id` 열과 조건부 외래키는 남아 있지만 사용하지 않는다. 접수 API·워커·브라우저 조회 함수는 준비되었고 실제 상담 화면 연결과 워커 스케줄러는 아직 없다.

## 학생에게 보이는 흐름

마지막 학생 발화의 텍스트가 확정되면 전문 저장·AI 최종 답변·생성 작업 접수를 병렬로 시작한다. 상담 시작 때 만든 `checkin_sessions.id`를 접수의 `session_id`로 전달한다. 전문 저장 전에도 접수할 수 있지만, 워커는 전문이 저장되고 세션이 종료된 작업만 실행한다. 전문을 기다리는 동안 AI 시도 횟수를 늘리거나 대체 아이템을 지급하지 않는다.

MVP의 접수·조회 API는 로그인 없이 seed의 민준 enrollment(`40000000-0000-4000-8000-000000000001`)에 속한 상담만 허용한다. 전문 저장 API와 실제 상담 종료 이벤트 연결은 상담 담당 작업이다. 다른 학생과 로그인 연동은 MVP 이후 작업이다.

`src/lib/items/itemGenerationClient.ts`의 `requestItemGeneration(sessionId)`를 전문 저장 및 최종 답변과 함께 호출한다. 접수 성공 후 `waitForItemGeneration(sessionId, "inference")`로 추출 결과를 기다리면 아이템 소개를 먼저 표시할 수 있다. 워커는 추출 결과를 저장한 직후 카탈로그 조회·필요 시 3D 조립을 계속한다. 브라우저의 조회는 워커를 실행하지 않으므로 별도 워커 호출이 필요하다.

섬 진입 버튼에서는 `waitForItemGeneration(sessionId, "placement")`로 최대 12초 기다린다. 준비되면 즉시 전환하고, `{ ready: false }`이면 생성 중 화면을 유지하고 다시 조회한다. 12초는 화면 대기 상한이며 작업 실패나 대체품 지급 조건이 아니다. `ready: true`는 지급된 에셋 참조가 있다는 뜻이고, 모델 다운로드·브라우저 렌더링 완료는 별도로 확인해야 한다. 현재 학생 화면은 목업이므로 이 함수의 화면 연결은 상담 담당 단계에서 한다.

생성이 일정 횟수 안에 끝나지 않으면 자동으로 고정된 선물 상자 설계 JSON을 지급한다. 이것은 임시 실패 화면이 아니라 완성된 Three.js 아이템이다.

학생이 자리를 비운 동안 서버 작업이 제한된 횟수로 다시 시도할 수 있다. 나중에 상담 기반 아이템이 완성되면 대체 아이템을 새 행으로 추가하지 않고, 같은 아이템의 설계와 종류를 교체한다. 학생이 배치한 위치·소유권·슬롯은 유지한다.

대체 아이템을 처음 지급할 때의 문구:

> 네 이야기를 담은 선물을 준비하고 있어. 기다리는 동안 이 선물을 먼저 받아줘.

백그라운드 작업으로 실제 아이템이 완성되어 교체된 경우에만 다음 문구를 보여준다.

> 어제 완성하지 못한 선물을 그 자리에 완성해 뒀어.

대체 아이템으로 최종 확정된 경우에는 완성되었다고 거짓으로 알리지 않는다. “먼저 준비한 선물을 간직해줘”처럼 대체 결과에 맞는 문구를 사용한다.

## 상태와 전이

권장 상태는 다음 여섯 가지다.

| 상태 | 의미 | 다음 상태 |
|---|---|---|
| `queued` | 생성 요청이 접수됨. 전문 저장 전에는 대기 | `generating` |
| `generating` | 소재 추론 또는 조립 AI 호출 중 | `completed`, `retry_wait`, `fallback` |
| `retry_wait` | 일시 오류 후 다음 시도를 기다림 | `generating`, `fallback` |
| `fallback` | 고정 대체 아이템을 먼저 지급하고 재시도를 남겨둔 상태 | `generating`, `fallback_final`, `completed` |
| `completed` | 상담 기반 아이템이 저장·지급된 상태 | 종료 |
| `fallback_final` | 백그라운드 재시도까지 실패해 대체품을 최종 확정 | 종료 |

`completed`와 `fallback_final`은 종료 상태다. 첫 시도 실패 시 `fallback`으로 즉시 대체품을 지급하고, 두 번째 시도는 백그라운드에서 진행한다. 브라우저가 닫혀도 작업 상태와 다음 시각은 DB에 남아야 한다.

## 재시도·비용 정책

무한 재시도는 하지 않는다. 합의한 기본값은 작업당 최대 2회의 AI 시도다. 첫 시도와 제한된 재시도 1회로 구성한다. 실제 값은 키 연결 후 응답 시간과 실패율을 보고 조정할 수 있지만, DB 기본 `max_attempts`는 2회다.

실패하면 먼저 실패 원인을 분류한다. 네트워크·429·일시적인 5xx는 재시도 대상이다. JSON 스키마 위반은 같은 입력을 반복하지 말고 한 번 단순화된 조립 요청으로 보낼 수 있다. 상담 전문 부족·동의·권한 오류는 생성 재시도로 해결하지 않는다. 모든 허용 시도를 사용하면 고정 대체 JSON을 사용한다.

대체품은 AI를 호출하지 않는 결정적 JSON이어야 한다. 따라서 API 장애가 길어져도 학생에게 아이템을 지급할 수 있고, 운영자가 개별 작업을 수리하지 않아도 된다. 백그라운드 성공 확률을 높이기 위해 더 비싼 모델로 무제한 재호출하지 않는다. 학생이 자리를 비운 동안의 재시도도 이 2회 상한에 포함한다.

## 같은 자리 교체

`20260917120000_1071_procedural_asset_storage.sql`은 `asset_catalog.asset_format`·`geometry_spec`과 `island_placements.current_asset_id`를 추가한다. 기존 GLB는 기본값 `glb`, 기존 배치는 NULL로 보존한다. 절차적 에셋은 검증된 조립 JSON을 `geometry_spec`에 저장하고, 렌더러는 `asset_format`으로 GLB/Three.js 경로를 선택한다.

fallback 지급 후 `student_items`의 불변 `asset_id`는 수정하지 않는다. 배치가 있으면 `island_placements.current_asset_id`만 generated asset으로 교체해 위치·student_item_id·획득 이력을 보존한다. NULL이면 기존처럼 `student_items.asset_id`를 표시한다. 실제 교체 RPC는 워커 단계에서 추가한다.

새 `student_items` 행을 fallback과 generated 각각에 만들지 않는다. 현재 마이그레이션은 배치의 현재 에셋 참조만 준비하며, 지급·교체 RPC는 워커 단계에서 멱등적으로 구현한다.

## DB 설계 시 결정할 것

`item_candidates`를 확장하지 않고 별도 `item_generation_jobs`를 만들기로 결정했다(`item_candidates`는 삭제). 이 테이블에는 다음 값이 있다.

- source session과 enrollment의 유일한 연결
- 현재 상태, 시도 횟수, `next_attempt_at`, 마지막 오류의 안전한 분류 코드
- fallback 지급 여부와 최종 확정 여부
- 최종 설계 JSON 또는 `asset_catalog`/학생별 결과 참조
- 작업 시작·완료 시각과 중복 claim을 위한 갱신 값

상담 종료 요청과 작업 접수는 멱등적이어야 한다. 같은 `source_session_id`로 두 번 요청해도 작업과 지급이 하나만 생겨야 한다. 작업자가 `queued`/`retry_wait` 행을 가져갈 때도 원자적 claim이 필요하다.

## 스케줄러 선택 보류

워커 자동 호출 방식은 2026-09-17 회의 이후 결정한다. 배포 서버가 확정되기 전에는 Vercel Cron, Supabase pg_cron/Edge Function, 별도 서버 cron 중 하나를 코드에 고정하지 않는다. 현재 `/api/internal/item-generation/worker`는 공통 실행 입구로 준비되어 있고, 선택한 환경이 이 URL을 인증 헤더와 함께 주기적으로 호출하면 된다.

cron을 사용하지 않는 대안은 학생의 다음 접속 때 워커를 호출하는 방식이다. 이 경우 학생이 다시 오기 전에는 fallback이 완성품으로 바뀌지 않는다. 회의에서 “학생 부재 중 자동 완성”을 유지할지와 배포 환경·호출 주기를 함께 결정한다.

## 다음 구현 순서

1. `20260917131000_1073_same_asset_replacement.sql`을 적용하고 타입을 갱신한다. (1070·1071·1072는 원격 적용 완료)
2. 기존 `asset_catalog`, `student_items`, `island_placements`의 실제 쓰기 정책과 불변 트리거를 다시 확인한다.
3. `/api/ai/item-generation`에 마지막 학생 발화 확정 후 POST를 전문 저장과 병렬로 연결한다. 같은 세션 POST는 기존 작업을 반환하고 GET은 추출 결과와 상태를 반환한다. 이 라우트는 접수·조회만 하며 AI를 오래 실행하지 않는다.
4. `/api/internal/item-generation/worker`가 비밀 Bearer 헤더로 호출되면 대기 중 가장 오래된 작업 하나만 `runItemGenerationJob(jobId)`로 실행한다. 워커는 성공 또는 2회 실패 후 `student_items`를 멱등 지급한다. 실제 cron 등록과 학생 화면 연결은 아직 없다.
5. fallback 지급 후 같은 위치를 교체할 저장 방식을 사용자와 확정하고 별도 마이그레이션·RPC를 만든다.
6. 브라우저 재접속 시 작업 상태와 완성 교체를 조회하도록 연결한다.
7. 키 연결 후 20명 규모에서 호출 수·실패율·완료 시간과 문구를 확인한다.

현재는 1번 조립 호출 함수와 제작기만 준비된 상태다. 이 문서의 상태·횟수·테이블 선택은 초안이며, 확정 전에는 스키마를 변경하지 않는다.
