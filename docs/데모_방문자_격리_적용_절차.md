## -1. 방어 계층을 헷갈리지 말 것 (정정)

이전 커밋 메시지에 "앱은 service_role로 우회해서 당장 앱 통한 유출은 없다"고 적었는데
오해를 부를 수 있는 문구였다 — **service_role은 RLS(RESTRICTIVE 포함) 전체를 그냥 우회한다.**
이 프로젝트에는 서로 겹치지 않는 두 개의 별개 방어 계층이 있다:

| 계층 | 무엇을 막나 | 누가 책임지나 |
|---|---|---|
| 앱 서버 코드 | 우리 Next.js 앱을 통한 접근 | `viewerTeacherId`/`demo_owner_id` 필터, `requireOwnSession` 등 소유권 검사(서버 코드) — 이게 실수로 빠지면 **RLS는 안 막아준다**(service_role 우회) |
| RLS(RESTRICTIVE 정책) | 앱을 거치지 않고 Supabase REST API/RPC를 직접 두드리는 경로 | 1092 마이그레이션 |

즉 "RLS를 고쳤으니 앱 코드는 안 봐도 된다"도, "앱 코드가 service_role을 쓰니 RLS는 몰라도
된다"도 둘 다 틀리다 — 둘 다 확인해야 한다. 실제로 이번 검토에서 앱 코드 쪽에서도 진짜 구멍을
하나 찾았다: `consultationLog.ts`의 `findClassConsultation()`이 상담 id만 맞으면 소유자
확인 없이 그 행을 돌려주고 있어서, 방문자 B가 A의 `parent_consultations.id`를 알아내면
A의 예정된 상담을 reschedule/complete할 수 있었다.

**(2026-09-20 갱신) 둘 다 이제 완전히 막혔다** — `findClassConsultation()`의 `viewerTeacherId`를
선택 인자에서 **필수 인자**로 바꿨다(값이 없으면 컴파일이 안 됨 → "빠뜨려서 검사가 생략되는"
경우 자체가 안 생긴다). `rescheduleConsultation()`의 호출부(`consultation/actions.ts`)도
서버에서 확인한 `teacher.id`를 넘기도록 고쳤다 — `completeScheduledConsultation()`은 이전
브랜치에서 이미 막혀 있었다. 아래 §7의 관련 항목도 "해결됨"으로 갱신.

## 0. 왜 순서가 중요한가

이번 변경에서 AI 호출 제한(`checkAndIncrementRateLimit`)을 **fail-closed**로 바꿨다 —
DB에 `increment_ai_rate_limit` 함수가 없으면(마이그레이션 미적용) 요청을 통과시키지 않고
502를 반환한다. 즉 **코드만 먼저 배포하고 마이그레이션을 나중에 적용하면, 그 사이 협진
챗봇이 팀원 전원에게 완전히 멈춘다.** 아래 순서를 반드시 지킨다: 마이그레이션을 먼저,
코드 배포(또는 로컬 `DEMO_MODE` 켜기)는 그다음.

## 1. 사전 준비 (Supabase 대시보드 설정)

1. Supabase 대시보드 → Authentication → Sign In / Providers → **Anonymous Sign-Ins 활성화**.
   로컬 `supabase/config.toml`도 `enable_anonymous_sign_ins = true`로 맞춘다(이미 스테이징
   완료 여부 확인 필요 — 이번 작업 범위에 포함 안 됐으면 여기서 먼저 켠다).
2. `supabase/config.toml`의 `anonymous_users` 레이트리밋(현재 IP당 시간당 30) 확인 — 심사
   당일 여러 명이 한 학교/사무실 네트워크에서 동시 접속하면 걸릴 수 있어 필요시 상향.
3. Vercel(또는 배포 환경) 환경변수에 `DEMO_MODE=true` 추가 — 이게 없으면 `src/proxy.ts`,
   `/api/demo/init`, `authorize.ts`/`_mockTeacherData.ts`의 데모 로직이 전부 비활성 상태로
   남는다(기존 동작 그대로, 안전한 기본값).

## 1-1. 익명 로그인을 켜기 전 점검 결과 (2026-09-20)

Supabase 문서의 주의점 3가지(익명 사용자도 `authenticated` 역할 / 캡차 권장 / 정적 렌더링 캐시)를 실제 DB·코드로 점검했다.

**① RLS — 익명 = `authenticated` (실제 DB 전수 조회)**
- 우리 설계에서 방문자는 의도적으로 담임 반 `assistant`다(`/api/demo/init`). 그래서 "그 반 교사면 읽기" 류 기존 정책이
  그대로 적용된다 → 1092가 소유자 컬럼이 있는 테이블을 좁혔지만, **덮지 못한 테이블이 있었다**. 켜기 전에는 익명
  방문자가 REST로 다음을 읽을 수 있었다(롤백 트랜잭션에서 `is_anonymous:true` JWT로 실측):
  `item_generation_jobs` 44건(AI 추론 결과·학생 메시지) · `student_items` 42건 · `feedback_drafts` 358건.
- 1093에 추가 → **적용 완료**(§2-3, 적용 후 익명 방문자 조회는 전부 0건, 개발 학생 본인은 자기 것 그대로):

  `island_placements`는 **JWT `is_anonymous`가 true면 거부**(`(auth.jwt() ->> 'is_anonymous')::boolean is not true`) —
  방문자가 직접 읽을 이유가 없는 테이블에만 썼다. teacher 정책 전체에 일괄로 걸면 방문자의 RLS 경로(예: vocab-growth)가
  깨지고, 우리 방어의 핵심(방문자 = 담임 반 assistant + 소유자 기준 격리)과도 맞지 않아서다.
- `ai_rate_limits`는 Supabase 기본값으로 `anon`/`authenticated`에 전체 DML 권한이 붙어 있었다(RLS로 지금도 거부).
  1093에서 권한 자체를 회수.
- 방문자가 쓸 수 있는 것: 공개 스키마 테이블에는 `authenticated`의 INSERT/UPDATE/DELETE 권한이 없고(9010이 회수), 스토리지
  버킷·정책은 없다. `TRUNCATE/TRIGGER/REFERENCES` 권한은 Supabase 기본값이지만 REST로는 노출되지 않는다.
- **`/api/demo/init` 권한 상승 결함 수정**: 이미 정식 로그인된 계정이 이 경로를 부르면 그 계정에 교사 프로필과 담임 반
  assistant 권한이 얹혔다 → 익명 세션(`is_anonymous`)에만 동작하도록 거부(403), 오류 응답의 DB 상세 메시지 제거, `no-store`.
- 알려진 노출(수용): `class_teachers_read`로 방문자가 같은 반의 다른 방문자 uid·role을 볼 수 있다. uid 자체는 비밀 토큰이
  아니고 접근 통제는 RLS/소유자 검사로 하지만, 원치 않으면 `class_teachers`에도 RESTRICTIVE를 추가한다.

**② 캡차·남용 방지 (미적용 — 결정 필요)**

**원칙: 데이터가 생성된 뒤에는 컬럼·테이블·인덱스를 삭제하는 복구를 자동으로 실행하지 않는다.**

### 8-1. 데모 기록이 아직 하나도 없을 때 (`demo_owner_id`가 방문자 UUID로 채워진 행 0건)
확인: `select count(*) from checkin_sessions where demo_owner_id is not null and id::text like '70000000-%';`
는 0이어야 하고, 방문자 익명 계정(`auth.users.is_anonymous`)이 0이어야 한다. 이 상태에서만 아래가 안전하다.
- RLS만 문제: `drop policy <이름> on <테이블>;` 7개 — 기존 팀 정책 그대로로 돌아간다.
- 1091: `drop function increment_ai_rate_limit(text,integer,integer); drop table ai_rate_limits;`
  (코드 쪽 `rateLimit.ts`가 fail-closed라 **코드를 먼저 되돌리거나 `DEMO_MODE=false`로 내린 뒤** 실행).
- 1090: 부분 유니크 인덱스 2개 삭제 → 원래 제약 복원
  `alter table checkin_sessions add constraint checkin_sessions_enrollment_id_session_date_period_attempt_key unique (enrollment_id, session_date, period, attempt);`
  → 필요하면 `demo_owner_id` 컬럼 2개 삭제. **주의: 1090이 재분류한 67건(개발 계정 소유)은 컬럼을 지우면 "누가
  만든 테스트인지" 정보도 같이 사라져 다시 공용처럼 보이게 된다** — 되돌릴 때 이 67건을 어떻게 볼지 먼저 결정.

### 8-2. 데모 기록이 생긴 뒤 (방문자 데이터가 1건이라도 있음) — 삭제형 복구 금지
- ⚠️ **`DEMO_MODE=false`는 안전한 복구가 아니다 (2026-09-20 코드 확인 + 실제 서버로 검증).** 플래그를 끄면 방문자
  격리(`lib/demo/scope.ts`)도 같이 꺼지는데, 교사 화면은 세션과 무관하게 `MOCK_TEACHER`로 열려 있다 —
  `DEMO_MODE` 미설정 서버에 **세션 쿠키 없이** 요청하면 `/dashboard`·`/observation`·`/consultation`·`/students`가
  전부 200(이건 원래 상태). 즉 끄는 순간 방문자들의 체크인 대화·분석이 그 교사 화면에 그대로 노출된다.
  (학생 쪽 체크인 API는 익명 계정이 학생 매핑이 없어 자연히 403.)
- **실제로 방문자 데이터 접근을 닫는 수단** (`src/proxy.ts`):
  ① **`DEMO_LOCKDOWN=true`** — 모든 데이터·교사·학생 경로가 세션과 무관하게 503. 실제 서버(`next start`)로 검증함:
  `/api/checkins/session`·`/api/teacher/meeting-requests`·`/dashboard`·`/observation`·`/demo-init`·`/api/ai/teacher-agent`
  전부 503, 매처 밖(`/`)은 200. Vercel은 환경변수 변경 후 **재배포**가 필요하다(즉시 반영 아님 — 급하면 Instant Rollback/배포
  일시 중지가 더 빠르다). ② `DEMO_MODE=false`일 때 **이미 발급된 익명 세션 쿠키**로 온 요청은 데이터 경로에서 403
  (`DEMO_ENDED`)으로 막는 코드를 추가했다 — **로직은 구현했지만 익명 로그인이 꺼져 있어 실제 익명 세션으로는 아직
  검증하지 못했다(미검증)**. 세션 쿠키 없는 요청은 위처럼 기존대로 열려 있다는 점은 그대로다.
- RLS RESTRICTIVE 정책 drop은 **데이터를 안 건드리지만 격리도 같이 사라진다** — 방문자 데이터가 다른 방문자에게
  RLS 경로로 노출될 수 있으니, drop 전에 `DEMO_MODE=false`로 앱 경로부터 막고, 직접 REST 접근 위험을 감수할지 판단한다.
- 컬럼(`checkin_sessions.demo_owner_id`, `analysis_runs.demo_owner_id`) 삭제 / 옛 unique 제약 복원은 **실행하지 않는다**:
  ① 삭제하면 누가 만든 기록인지 영구히 잃고 ② 같은 (enrollment, 날짜, 교시, attempt)에 방문자별 행이 여러 개 쌓여 있으면
  옛 제약 복원이 충돌로 실패한다. 꼭 필요하면 (a) 방문자 행을 별도 테이블로 내보내기·백업 → (b) 대상 행 목록을
  사람이 확인 → (c) 수동 실행 순서로만 진행한다.
- 봉인된 기록(`parent_consultations` 완료, `work_records`)은 트리거 때문에 서비스 롤로도 수정·삭제가 안 된다 —
  그 데이터를 지우는 복구는 애초에 불가능하다(설계상).
- 개발 계정 소유로 재분류한 67건을 되돌리려면(공용으로 복귀) 팀이 그 행이 공용으로 써도 되는 데이터인지
  확인한 뒤 `update checkin_sessions set demo_owner_id = null where id in (<확인된 id 목록>)`만 수동 실행.

## 10. 익명 로그인 브라우저 이전(b안) + Turnstile 켜는 순서 (2026-09-20)

**변경**: `signInAnonymously()`를 서버(`/api/demo/init`)에서 브라우저의 `/demo-init` 화면으로 옮겼다. 이유: ① 서버에서 부르면 Supabase가 보는
IP가 Vercel 서버 IP라 익명 로그인 레이트리밋(IP당 시간당 30회)을 **전체 방문자가 공유**한다 ② 캡차 토큰은 브라우저에서만 얻는다.
`/api/demo/init`은 이미 만들어진 익명 세션에 프로필·담당 학급을 준비하는 일만 한다(세션이 없으면 401 `NO_SESSION`, 정식 로그인 계정이면 403).
`/demo-init`은 ① 세션 확인 ② `NEXT_PUBLIC_TURNSTILE_SITE_KEY`가 있으면 Turnstile 위젯(`interaction-only` — 사람이 확실하면 보이지 않음)
③ `signInAnonymously({ options: { captchaToken } })` ④ `/api/demo/init` ⑤ 원래 경로 순서로 진행한다. StrictMode 이중 실행에도 로그인은
한 번만(`useRef` 가드), `?next=`는 사이트 안 경로만 허용(오픈 리다이렉트 방지).

**검증 상태**: 빌드·린트 통과, 서버 쪽은 실제 서버로 확인(세션 없는 `init` 401 / 정식 게이트·리다이렉트 / `DEMO_MODE` 꺼짐 시 404).
**브라우저 쪽(위젯 렌더, 토큰 → 로그인, 쿠키 발급, 리다이렉트)은 미검증** — Anonymous Sign-Ins가 꺼져 있고 Turnstile 키가 아직 없다.

**켜는 순서 (반대로 하면 전원 로그인 실패)**
1. Cloudflare → Turnstile → 위젯 추가. 도메인: Vercel 도메인(프리뷰 포함 시 `*.vercel.app` 또는 각 도메인)과 `localhost`.
2. **사이트 키** → Vercel 환경변수 `NEXT_PUBLIC_TURNSTILE_SITE_KEY`(공개값), `DEMO_MODE=true` → **이 값을 넣은 배포를 먼저 완료**.
3. Supabase → Authentication → Sign In / Providers → **Anonymous Sign-Ins 켜기**.
4. **로컬 회귀 확인(§5)을 이 시점 전에 끝낸다.** 캡차를 켜면 `/api/dev/login`(`signInWithPassword`)이 막힌다.
5. Supabase → Authentication → Attack Protection → **CAPTCHA 켜기 → Turnstile → 시크릿 키 입력**(시크릿은 앱이 아니라 여기에만).
6. 팀에 "○시에 캡차를 켜면 로컬 로그인이 막힌다"고 미리 공지.
7. 켠 뒤 시크릿 창으로 `/checkin` 진입 → 위젯 통과 → 체크인 화면이 뜨는지, Supabase Users에 익명 계정이 1개 생기는지 확인.
   (개발용으로 위젯을 시험하려면 Cloudflare의 테스트 키 `1x00000000000000000000AA`(항상 통과)를 사이트 키로, 시크릿은
   `1x0000000000000000000000000000000AA`를 Supabase에 넣어 본 뒤 실제 키로 교체.)

1. **3단 한도를 한 함수로**: `enforceAiLimits({ route, viewerId, ip })`가 ① 방문자 ② IP ③ **전체 일일 총량** 순서로 검사한다.

2. **모든 AI 경로에 적용**: chat·transcribe·daily-analysis·comment-draft·vocab-growth·item-generation·teacher-agent(기존 30회를 이 함수로 통합).
   vocab-growth는 요청 횟수와 **한 요청당 추출 건수(12)** 둘 다 제한, item-generation은 방문자당 시간당 세션 수 제한.
3. **권장 초기값(예산으로 조정)** — 방문자/시간: chat 60턴, transcribe 30, teacher-agent 30, daily-analysis·comment-draft 20, item-generation 6,

   (`AI_DAILY_MAX_<ROUTE>`)로 두어 재배포 없이(=환경변수 변경 후 재배포는 필요) 조정할 수 있게 한다. 코드에 숫자를 박지 않는다.
4. **총량 소진 시 우아한 저하**: 학생 대화는 고정 응답(`fixed`)으로, 분석·초안은 캐시/목업으로 대체하고 화면에 안내 — 데모가 멈추지 않게.
5. **공급자 측 하드 캡(가장 확실한 최후 방어)**: OpenAI·Anthropic 콘솔에서 **월 지출 한도(spend limit)와 알림**을 설정한다. 앱 코드 버그가 있어도
   이 한도는 넘지 않는다. (콘솔 설정이라 제가 대신 못 한다.)
6. 남은 위험: IP는 `x-forwarded-for`에 의존(Vercel이 채워 주지만 신뢰 경계 확인 필요), 카운터가 `+1` 고정이라 **길이에 비례하는 비용

### 13-2. 설계 요약 (사용자 확정 사항 반영)
- **유니크 인덱스는 부분 인덱스 3분할**(공용 / 방문자 `owner IS NOT NULL` / 레거시 `owner IS NULL AND NOT is_public_demo`): `student_items_daily_slot`·`_daily_core`·`islands_enrollment_id_key`를 교체. zero-uuid `coalesce`는 쓰지 않는다(공용·레거시가 모두 owner NULL이라 충돌).
- **DB 트리거**: `student_items` INSERT 시 `demo_owner_id`가 부모 세션(및 그 세션의 job) 소유자와 다르면 거부, 부모 없는 비공용 아이템 거부, 공용 행은 시드 관리 세션(`set_config('salpim.seed_admin','on',true)`)에서만 생성. `islands`/`island_placements`는 공용 행 수정·삭제 거부 + 아이템·섬 소유자 일치 강제.
- **RPC `place_demo_item`/`remove_demo_placement`**: 개인 섬 생성 + 배치 저장을 한 트랜잭션으로, **`p_owner_id`를 믿지 않고** 아이템·부모 세션·생성 job 소유자와 모두 대조. `auth.uid()`는 서버가 service_role로 부르므로 쓸 수 없어(JWT 없음) 채택하지 않았고, 대신 `public/anon/authenticated` EXECUTE를 **명시적으로 revoke → `service_role`에만 grant**(마이그레이션 마지막 `DO` 블록이 `has_function_privilege`로 자체 검증). 같은 아이템의 중복 배치는 `unique(student_item_id)` + upsert(이동)로 막고, 겹침은 섬 행 `FOR UPDATE` 잠금 안에서 `footprint_radius`로 다시 검사한다.
- **서버 좌표 검증**: 공용 배치 ∪ 내 배치를 읽어 씬과 같은 규칙(`placementRules.ts`: 조각 안·테두리 여유·지형·아이템 반경 겹침)으로 검증한 뒤 RPC 호출.
- **`asset_catalog_read` 교체(E-3)**: 정식 로그인은 기존대로 전체, 익명 방문자는 공용 아이템 또는 본인 `demo_owner_id` 아이템(·본인 배치의 교체 자산)이 참조하는 자산만. 알려진 잔여: `dedup_key`로 같은 이름 아이템은 한 자산을 공유하므로 그 자산은 참조한 모든 소유자에게 보인다.
- 기존 42건은 `student_items_immutable` 때문에 backfill 불가·불필요 → 그대로 "레거시"로 남고 방문자에게는 계속 안 보인다.

개발 서버 로그(응답에 실린 `TurbopackInternalError`)의 원인: `Failed to write app endpoint … → [project]/src/app/globals.css → PostCssTransformedAsset::process → creating new process → node process exited before we could connect to it with exit code: 0xc0000142`. 즉 **Turbopack이 PostCSS를 돌릴 자식 node 프로세스를 못 띄우는** 상태다(0xc0000142 = Windows DLL 초기화 실패, 오래 떠 있던 개발 서버 프로세스의 자원 문제로 흔하다).
- 이번 변경 코드와 무관하다는 근거: (1) 변경하지 않은 `/island`, 기존 `/item-lab/minjun-island`도 같은 오류로 500, (2) 실패 지점이 `globals.css`의 PostCSS 프로세스 생성이지 모듈 컴파일이 아님, (3) 같은 소스의 `next build`(프로덕션)는 성공하고 프로덕션 서버에서 두 페이지가 200.
- 한 번 재시도해도 동일했다(무한 재시도 안 함). 해결: 실행 중인 개발 서버(`next dev`, 포트 3000)를 재시작한다.

### 14-5. 롤백 판단 기준
- **1단계 직후~시드 전(방문자 데이터 0건)**: 문제가 있으면 `1094_demo_shared_island_rollback.sql` 전체 롤백(1093 상태 복원). 아이템 지급이 계속 실패하거나 정책이 방문자 화면을 깨면 이 경로.
- **시드 이후 / 방문자 데이터가 생긴 뒤**: 전체 롤백은 스크립트가 거부한다(컬럼·행 삭제 금지, §8-2). 정책만 잠그는 "부분 롤백" 블록을 쓴다. 공용 시드 자체를 되돌려야 하면 별도 승인으로 봉인 트리거를 잠시 끄고 공용 행만 삭제한다.
- 앱 코드 문제만이면 DB는 두고 코드를 되돌린다(이 경우 구 코드는 아이템 지급이 실패하므로 **구 코드로 되돌릴 때는 DB 롤백이 함께 필요**하다 — 둘은 한 쌍이다).

### 14-6. 알려진 한계 (적용 후에도 남는 것)
- `dedup_key`로 같은 이름 아이템은 한 자산을 공유하므로 그 자산은 참조한 모든 소유자에게 보인다(`asset_catalog` 정책의 구조적 한계).
- 배치 저장 실패(서버 좌표 거부·네트워크)는 화면에 알리지 않고 콘솔 경고만 남긴다.
- 방문자별 개인 섬은 첫 배치 때 만들어진다(체크인만 하고 배치를 안 한 방문자에게는 섬 행이 없다).
- 두 방문자의 진짜 동시 배치 경합, WebGL 렌더링은 자동 검증하지 못했다(공용 15종의 모양·배치는 사용자가 화면으로 확인).
