# 공개 데모 방문자 격리 — 마이그레이션 적용 순서 · 통합 테스트 절차

> 설계 배경·근거: `C:\Users\lee_j\.claude\plans\cozy-mixing-scone.md`(계획 문서, 로컬)
> 관련 브랜치: `feature/jihyeon-demo-anon-isolation`
>
> ⚠️ **이 문서에 있는 절차를 실제로 밟고, 6번(A/B 격리 테스트)까지 통과하기 전에는
> 이 브랜치를 main에 merge하지 않는다.** 공유 DB에도 아직 마이그레이션을 적용하지 않았다.

## 0. 왜 순서가 중요한가

이번 변경에서 AI 호출 제한(`checkAndIncrementRateLimit`)을 **fail-closed**로 바꿨다 —
DB에 `increment_ai_rate_limit` 함수가 없으면(마이그레이션 미적용) 요청을 통과시키지 않고
502를 반환한다. 즉 **코드만 먼저 배포하고 마이그레이션을 나중에 적용하면, 그 사이 협진
챗봇이 팀원 전원에게 완전히 멈춘다.** 아래 순서를 반드시 지킨다: 마이그레이션을 먼저,
코드 배포(또는 로컬 `DEMO_MODE` 켜기)는 그다음.

## 1. 사전 준비 (Supabase 대시보드 설정)

1. Supabase 대시보드 → Authentication → Sign In / Providers → **Anonymous Sign-Ins 활성화**.
   로컬 `supabase/config.toml`도 `enable_anonymous_sign_ins = true`로 맞춘다(이미 스테이징
   완료 여부 확인 필요 — 이번 작업 범위에 포함 안 됐으면 여기서 먼저 켠다).
2. `supabase/config.toml`의 `anonymous_users` 레이트리밋(현재 IP당 시간당 30) 확인 — 심사
   당일 여러 명이 한 학교/사무실 네트워크에서 동시 접속하면 걸릴 수 있어 필요시 상향.
3. Vercel(또는 배포 환경) 환경변수에 `DEMO_MODE=true` 추가 — 이게 없으면 `src/proxy.ts`,
   `/api/demo/init`, `authorize.ts`/`_mockTeacherData.ts`의 데모 로직이 전부 비활성 상태로
   남는다(기존 동작 그대로, 안전한 기본값).

## 2. 마이그레이션 적용 순서

**반드시 이 순서대로**(뒤 마이그레이션이 앞 마이그레이션이 만든 컬럼·정책을 전제한다):

1. `20260920013300_1090_demo_owner_isolation.sql`
   — `checkin_sessions.demo_owner_id` 컬럼 + 부분 유니크 인덱스 두 개로 교체.
2. `20260920020400_1091_ai_rate_limits.sql`
   — `ai_rate_limits` 테이블 + `increment_ai_rate_limit()` 함수.
3. `20260920021300_1092_demo_owner_restrictive_rls.sql`
   — RESTRICTIVE 정책 5개(checkin_sessions, conversation_messages, work_records,
   work_record_students, conflict_statements). **1090이 먼저 적용돼 있어야** `demo_owner_id`
   컬럼을 참조하는 정책이 성공한다.

적용 방법(팀 Supabase CLI 보유자 기준):
```
supabase db push          # 또는 supabase migration up, 팀 워크플로우에 맞게
```
CLI가 없으면 Supabase 대시보드 SQL Editor에서 위 3개 파일 내용을 **순서대로** 실행.

적용 직후 확인:
```sql
-- 1090 확인
select column_name from information_schema.columns
where table_name = 'checkin_sessions' and column_name = 'demo_owner_id';

-- 1091 확인
select proname from pg_proc where proname = 'increment_ai_rate_limit';

-- 1092 확인 (restrictive 5개가 다 보여야 함)
select tablename, policyname, permissive from pg_policies
where policyname like '%demo_owner_restrict';
```

## 3. `database.types.ts` 재생성

이번 브랜치는 `src/lib/supabase/database.types.ts`(원래 `supabase gen types`로 자동 생성)를
**수동으로 patch**해뒀다(`demo_owner_id` 컬럼, `increment_ai_rate_limit` 함수 시그니처) —
마이그레이션이 실제로 적용된 뒤, 아래로 다시 생성해서 수동 patch를 정식 생성 결과로 덮어쓴다:
```
supabase gen types typescript --project-id <project-ref> > src/lib/supabase/database.types.ts
```
재생성 후 `npm run build`로 타입이 그대로 맞는지 재확인(수동 patch와 실제 생성 결과가 다르면
빌드가 알려준다).

## 4. 로컬 검증 (마이그레이션 적용 + 코드 배포 전, 로컬에서 먼저)

1. `.env.local`에 `DEMO_MODE=true` 추가.
2. `npm run build && npm run start` — `next dev`가 아니라 **build+start**로 실제
   `NODE_ENV=production`을 재현한다(로컬 dev 우회 로직이 안 섞이게).
3. 로그인 없이 `/checkin` 접속 → `/demo-init`으로 리다이렉트되는지 확인 → 초기화 후 원래
   경로로 돌아오는지 확인.
4. 체크인 완료 → Supabase 대시보드에서 `checkin_sessions.demo_owner_id`에 실제 익명
   `auth.users.id`가 채워졌는지 확인.
5. 교사 화면(`/observation`, `/consultation`, `/dashboard`)에 접속 → `profiles`,
   `class_teachers`(role='assistant')에 방문자 행이 생겼는지 확인.

## 5. `/api/dev/login` 회귀 확인 (로컬 개발 흐름 안 깨졌는지)

1. `.env.local`에서 `DEMO_MODE`를 지우거나 `false`로.
2. `npm run dev` (일반 개발 모드) → `/api/dev/login` 접속 → 기존처럼 로그인되는지,
   `/checkin`이 문제없이 동작하는지 확인. proxy.ts는 기존 세션(익명이든 아니든)을 건드리지
   않고 통과시키므로 이 흐름은 안 바뀌어야 정상.

## 6. A/B 격리 테스트 (★ 이걸 통과해야 main merge 가능)

**서로 다른 브라우저(또는 별도 프로필) 2개**를 쓴다 — 같은 브라우저의 시크릿 창끼리는
쿠키를 공유할 수 있어 신뢰 못 한다.

| # | 절차 | 기대 결과 |
|---|---|---|
| 1 | A: `/checkin`부터 진입, 체크인 완료 | A만의 `checkin_sessions` 행 생성 |
| 2 | B: `/dashboard`(교사 화면)부터 진입 — 학생 경로 안 거침 | proxy.ts가 교사 경로에서도 세션을 잡아 `/demo-init`으로 보내는지 확인(이전 설계의 "학생 경로만" 구멍이 진짜로 막혔는지) |
| 3 | B: 체크인도 진행, A와 다른 색·다른 대화 입력 | B만의 `checkin_sessions` 행 생성, A 것과 안 섞임 |
| 4 | A, B 각자 관찰일지 새로 작성(다른 내용) | 각자 `work_records.created_by`가 자기 auth.uid()로 저장 |
| 5 | A의 교사 화면에서 관찰일지 목록·상담 목록·대시보드 확인 | 공용 시드 + A가 쓴 것만 보이고, B가 쓴 건 안 보임 |
| 6 | B의 교사 화면에서 동일 확인 | 공용 시드 + B가 쓴 것만 보이고, A가 쓴 건 안 보임 |
| 7 | A, B 각자 협진 챗봇에 "오늘 민준이 어때?" 질문 | 자기가 방금 입력한 체크인·기록만 근거로 답변(상대방 내용 언급 없음) |
| 8 | **공격적 테스트**: A가 B의 `checkin_sessions.id`/`parent_consultations.id`를 (DB에서 직접 확인 후) URL·API 요청에 넣어 조회 시도 | 403/404로 거부 — `requireOwnSession`의 `demo_owner_id` 대조가 실제로 막는지 확인 |
| 9 | 같은 방문자(A)가 체크인 버튼을 거의 동시에 두 번 클릭 | `checkin_sessions` 행이 한 건만 생김(동시 클릭 경합 테스트) |
| 10 | AI 호출 30회 초과 시도(한 방문자로 연속 호출) | 429 응답, 이후 시간창 지나면 다시 허용 |
| 11 | (선택) Supabase 대시보드에서 B의 익명 계정으로 REST API를 직접 호출해 A의 `work_records`/`checkin_sessions` 조회 시도 | RLS RESTRICTIVE 정책이 막아 빈 결과 — 1092 마이그레이션이 실제로 동작하는지 최종 확인 |

## 7. 알려진 미해결 범위 (이번 절차로 안 잡히는 것)

- `feedback_drafts`/`feedback_sources`(교사 코멘트 AI 초안), `analysis_runs`(AI 분석 결과)는
  구조상 방문자별 소유 컬럼이 없어서 이번 작업 범위 밖 — RLS도 앱 코드도 아직 방문자별로
  안 나뉜다. 위 A/B 테스트에 이 두 기능은 포함하지 말 것(아직 안 막혀 있다는 걸 알고 있는
  상태 그대로 둠).
- `dashboard`의 "예정된 상담"(`listScheduledConsultationsOn`), 자리 배치 관련 조회는
  `viewerTeacherId`를 아직 안 흘려보냄.
- 오래된 데모 데이터 정리(자동 만료)는 봉인 트리거 때문에 이번 범위에서 뺐다 —
  `docs/데모_방문자_격리_쿠키_방식.md` §7, 계획 문서 G항 참고.

## 8. 문제 생기면 (롤백)

- RLS RESTRICTIVE 정책만 문제면: `drop policy <이름> on <테이블>;` 5개만 걷어내도 이전
  상태(느슨하지만 기존 팀원 정책 그대로)로 돌아간다 — 1090/1091은 안전하게 유지 가능.
- `demo_owner_id` 컬럼/인덱스 되돌리기가 필요하면: 새 부분 유니크 인덱스 2개를 지우고
  원래 `unique(enrollment_id, session_date, period, attempt)` 제약을 다시 만든다(단, 이미
  같은 (enrollment_id, session_date, period, attempt) 조합에 서로 다른 demo_owner_id로
  여러 행이 쌓였다면 원래 제약으로 복귀 시 충돌 — 데모 기간 중 롤백은 신중히).
- `DEMO_MODE`를 `false`로 내리면 코드 쪽 신규 로직(proxy.ts 게이트, requireStudent 데모 분기,
  getActingTeacher 데모 분기)이 전부 비활성화되고 기존 동작으로 즉시 복귀한다 — 가장 빠른
  임시 롤백 수단.
