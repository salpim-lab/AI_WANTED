## -1. 방어 계층을 헷갈리지 말 것 (정정)

이전 커밋 메시지에 "앱은 service_role로 우회해서 당장 앱 통한 유출은 없다"고 적었는데
오해를 부를 수 있는 문구였다 — **service_role은 RLS(RESTRICTIVE 포함) 전체를 그냥 우회한다.**
이 프로젝트에는 서로 겹치지 않는 두 개의 별개 방어 계층이 있다:

| 계층 | 무엇을 막나 | 누가 책임지나 |
|---|---|---|
| 앱 서버 코드 | 우리 Next.js 앱을 통한 접근 | `viewerTeacherId`/`demo_owner_id` 필터, `requireOwnSession` 등 소유권 검사(서버 코드) — 이게 실수로 빠지면 **RLS는 안 막아준다**(service_role 우회) |
| RLS(RESTRICTIVE 정책) | 앱을 거치지 않고 Supabase REST API/RPC를 직접 두드리는 경로 | 1092 마이그레이션 |

즉 "RLS를 고쳤으니 앱 코드는 안 봐도 된다"도, "앱 코드가 service_role을 쓰니 RLS는 몰라도
된다"도 둘 다 틀리다 — 둘 다 확인해야 한다. 실제로 이번 검토에서 앱 코드 쪽에서도 진짜 구멍을
하나 찾았다: `consultationLog.ts`의 `findClassConsultation()`이 상담 id만 맞으면 소유자
확인 없이 그 행을 돌려주고 있어서, 방문자 B가 A의 `parent_consultations.id`를 알아내면
A의 예정된 상담을 reschedule/complete할 수 있었다.

**(2026-09-20 갱신) 둘 다 이제 완전히 막혔다** — `findClassConsultation()`의 `viewerTeacherId`를
선택 인자에서 **필수 인자**로 바꿨다(값이 없으면 컴파일이 안 됨 → "빠뜨려서 검사가 생략되는"
경우 자체가 안 생긴다). `rescheduleConsultation()`의 호출부(`consultation/actions.ts`)도
서버에서 확인한 `teacher.id`를 넘기도록 고쳤다 — `completeScheduledConsultation()`은 이전
브랜치에서 이미 막혀 있었다. 아래 §7의 관련 항목도 "해결됨"으로 갱신.

## 0. 왜 순서가 중요한가

이번 변경에서 AI 호출 제한(`checkAndIncrementRateLimit`)을 **fail-closed**로 바꿨다 —
DB에 `increment_ai_rate_limit` 함수가 없으면(마이그레이션 미적용) 요청을 통과시키지 않고
502를 반환한다. 즉 **코드만 먼저 배포하고 마이그레이션을 나중에 적용하면, 그 사이 협진
챗봇이 팀원 전원에게 완전히 멈춘다.** 아래 순서를 반드시 지킨다: 마이그레이션을 먼저,
코드 배포(또는 로컬 `DEMO_MODE` 켜기)는 그다음.

## 1. 사전 준비 (Supabase 대시보드 설정)

1. Supabase 대시보드 → Authentication → Sign In / Providers → **Anonymous Sign-Ins 활성화**.
   로컬 `supabase/config.toml`도 `enable_anonymous_sign_ins = true`로 맞춘다(이미 스테이징
   완료 여부 확인 필요 — 이번 작업 범위에 포함 안 됐으면 여기서 먼저 켠다).

   당일 여러 명이 한 학교/사무실 네트워크에서 동시 접속하면 걸릴 수 있어 필요시 상향.

1. `20260920013300_1090_demo_owner_isolation.sql`

2. `20260920020400_1091_ai_rate_limits.sql`
   — `ai_rate_limits` 테이블 + `increment_ai_rate_limit()` 함수.
3. `20260920021300_1092_demo_owner_restrictive_rls.sql`
   — RESTRICTIVE 정책 **7개**(checkin_sessions, conversation_messages, work_records,
   work_record_students, conflict_statements, meeting_requests, **analysis_runs**). **1090이
   먼저 적용돼 있어야** `demo_owner_id` 컬럼을 참조하는 정책이 성공한다.

적용 방법(팀 Supabase CLI 보유자 기준):
```
supabase db push          # 또는 supabase migration up, 팀 워크플로우에 맞게
```
CLI가 없으면 Supabase 대시보드 SQL Editor에서 위 3개 파일 내용을 **순서대로** 실행.

적용 직후 확인:
```sql
-- 1090 확인 (checkin_sessions, analysis_runs 둘 다 나와야 함)
select table_name, column_name from information_schema.columns
where column_name = 'demo_owner_id' and table_name in ('checkin_sessions', 'analysis_runs');

-- 1091 확인
select proname from pg_proc where proname = 'increment_ai_rate_limit';

-- 1092 확인 (restrictive 7개가 다 보여야 함)
select tablename, policyname, permissive from pg_policies
where policyname like '%demo_owner_restrict';
```

- ~~`analysis_runs` 격리 범위 밖~~ **(2026-09-20 해결, 단 조건부)** — 스키마(전용
  `demo_owner_id` 컬럼)와 RLS(RESTRICTIVE 정책)는 5개 source_type 전부 다룬다. 다만 실제
  효력은 지금 이 테이블에 쓰는 코드 상태에 따라 다르다:
  - `source_type='session'`(감정 어휘 캐시, `lib/vocab/liveVocab.ts` + `/api/ai/vocab-growth`):
    실제 Supabase 테이블에 쓰고 있고, 그중 `/api/ai/vocab-growth`는 RLS가 적용되는 세션
    클라이언트(`createClient()`)를 쓰므로 **이번 RESTRICTIVE 정책이 배포 즉시 유효**하다.
    `liveVocab.ts`는 admin 클라이언트(service_role)로 쓰지만, 그 write 자체는 RLS 우회와
    무관하게 이 정책이 이후의 RLS 경유 조회를 계속 막아준다.
  - `source_type='student'`(상담 리포트 "기간 요약", `_lib/periodSummary.ts`)와 하루 분석

    메모리 목업(`mockAnalysisRuns`, `globalThis`)에 쓴다** — 이 정책의 적용 대상 자체가 아니다.
    다만 이 목업은 캐시 키 자체가 이미 방문자별로 자연히 갈린다고 판단했다: dailyAnalysis는
    `sessionId`(이미 방문자마다 다른 체크인 세션 행)로, periodSummary는 입력에 쓰인
    analysis·observation id 목록(`sourceKey`, 이미 viewerTeacherId로 걸러진 값)으로 캐시를
    구분해서, 공용 데이터만으로 만든 요약은 공유돼도 안전하고(내용이 같은 공용 데이터라서)
    방문자 본인 기록이 섞이면 키가 달라져 자연히 분리된다 — 단, 이건 "우연히 안전한" 상태지
    설계로 보장한 게 아니라서, 이 두 파일을 실제 `analysis_runs`로 옮길 때는 반드시
    `demo_owner_id`를 채우고 조회도 걸러야 한다(각 파일에 TODO 주석 남겨둠).
  - `source_type='record'`·`'class'`: 지금 이 두 source_type으로 쓰는 앱 코드 자체가 없다 —
    정책만 미리 준비해뒀다(다음에 이 source_type을 쓰는 코드가 생기면 그대로 적용됨).
  - `feedback_drafts`/`feedback_sources`(교사 코멘트 AI 초안)는 여전히 범위 밖 — `created_by`가
    'ai'|'teacher' 라벨일 뿐 방문자를 구분할 owner 컬럼 자체가 없고, 앱 코드(comment-draft
    라우트)도 아직 방문자별로 안 나눈다. 위 A/B 테스트에 이 기능은 포함하지 말 것.
- `dashboard`의 "예정된 상담"(`listScheduledConsultationsOn`), 자리 배치 관련 조회는
  `viewerTeacherId`를 아직 안 흘려보냄.
- `lib/vocab/liveVocab.ts`(대시보드 감정 어휘 카드, 진승혜 소유)는 애초에 "민준이의 가장 최근
  체크인 세션 하나"를 방문자 구분 없이 admin 클라이언트로 조회한다 — 여러 방문자가 동시에
  체크인하면 그 카드는 방문자 중 누구든 가장 최근에 체크인한 사람의 어휘를 보여준다(대시보드는
  원래 "학급 전체 공용 화면"으로 설계돼 있어 이번 관찰일지·상담기록처럼 viewerTeacherId로
  나누는 대상에 안 들어가 있었다). 이번 analysis_runs 작업의 범위는 **테이블 자체의 RLS/스키마
  격리**였고, 이 카드가 "누구 세션을 보여줄지 고르는" 로직은 별도 UX 결정이 필요한 사안이라
  이번 브랜치에서는 건드리지 않았다 — 팀에 공유는 해둘 것.
- 오래된 데모 데이터 정리(자동 만료)는 봉인 트리거 때문에 이번 범위에서 뺐다 —
  `docs/데모_방문자_격리_쿠키_방식.md` §7, 계획 문서 G항 참고.

## 8. 문제 생기면 (롤백)

- RLS RESTRICTIVE 정책만 문제면: `drop policy <이름> on <테이블>;` 7개만 걷어내도 이전
  상태(느슨하지만 기존 팀원 정책 그대로)로 돌아간다 — 1090/1091은 안전하게 유지 가능.
- `demo_owner_id` 컬럼/인덱스 되돌리기가 필요하면: 새 부분 유니크 인덱스 2개를 지우고
  원래 `unique(enrollment_id, session_date, period, attempt)` 제약을 다시 만든다(단, 이미
  같은 (enrollment_id, session_date, period, attempt) 조합에 서로 다른 demo_owner_id로
  여러 행이 쌓였다면 원래 제약으로 복귀 시 충돌 — 데모 기간 중 롤백은 신중히). `analysis_runs.
  demo_owner_id`는 유니크 제약이 없는 단순 컬럼이라 `drop column`만으로 되돌릴 수 있다(단,
  그 시점에 이미 이 컬럼을 참조하는 정책이 있으면 정책부터 지워야 한다).
- `DEMO_MODE`를 `false`로 내리면 코드 쪽 신규 로직(proxy.ts 게이트, requireStudent 데모 분기,
  getActingTeacher 데모 분기)이 전부 비활성화되고 기존 동작으로 즉시 복귀한다 — 가장 빠른
  임시 롤백 수단.
