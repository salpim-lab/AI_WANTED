# 학생 대화 화면 설계 — 로직 · 감정 추론 근거 · 스키마

> 작성: 2026-09-17 · 이유민
> 이 문서는 대화 화면(3단계)의 동작 규칙과, 거기서 나오는 데이터를
> 교사 화면이 어떻게 쓰는지, 그리고 그 판단의 근거가 무엇인지를 정한다.
>
> 대화 화면은 **이후 모든 화면의 재료를 만드는 단계**다. 여기서 남기지 않은 것은
> 교사 화면에서도, 아이템에서도, 리포트에서도 쓸 수 없다.

---

## 1. 대화 로직

### 1.1 전체 흐름

```
마음 색 선택
  ↓
① 고정 첫 질문                      ← API 호출 없음
  ↓
② 아이 발화 (음성 → STT)
  ↓
③ 판단
   ├ 위험 신호      → 하드 게이트 (아래 1.3)
   ├ 충분히 상세    → 마무리 인사, 종료
   └ 부족           → 유도 질문 1회 (여기에만 맥락 주입)
                       ↓
                     아이 발화 → 무조건 종료
  ↓
④ 종료 후 면담 신청 버튼 노출
```

**세션당 상한: 2턴 · LLM 최대 2회 · STT 최대 2회.**

### 1.2 첫 질문은 고정이다

색만으로는 개인화할 재료가 없다. 아이 발화가 아직 없기 때문이다.
색으로 분기하는 것은 템플릿이 하는 일과 같다.

- 기획안 "색 3초" 예산 — API 왕복이 들어가면 첫 화면이 늦는다
- 비용표에 이미 **"TTS (고정 질문 사전 생성) $0.2"** 가 있다. 고정이 전제였던 설계다

**변주는 색당 2~3개를 요일로 돌려서 준다.** 매일 같은 말은 피하고 비용은 0이다.

### 1.3 게이트 — 언제 묻지 않을지

기획안 §8.6 이 이 제품에서 가장 중요한 기술 설계라고 못 박은 부분이다.

> **유도 질문은 증거를 파괴합니다.** 아동 학대·학교폭력 사안에서 아동 진술의 신빙성은
> 유도 질문 여부로 다투어집니다. AI 가 "누가 때렸어?" 라고 물으면 그 시점부터
> 진술 전체가 오염된 것으로 취급될 수 있습니다.

| 게이트 | 동작 |
|---|---|
| **위험 신호** (신체 위해·학대·자해) | 후속 질문 **전면 중단** → "그건 선생님한테 직접 얘기해줄래?" → 교사 즉시 알림 → 그 시점까지 기록 봉인 |
| 회피 신호 2회 | 종료 |
| 2턴 도달 | 무조건 종료 |

위험 신호에서 AI 는 **위로도 상담도 하지 않는다.** 한 마디 하고 교사에게 넘긴다.
기획안 원칙표: *"판정 금지 — 진단·점수·위험도 없음"*, *"유도 질문 금지"*.

구현은 `meeting_requests` 에 `requested_by='system'`, `priority='high'` 로 넣는다.
스키마가 이미 이 경로를 받는다.

### 1.4 색상별 동작

| 색 | 첫 질문 성격 | 턴 |
|---|---|---|
| 초록 | 자랑·좋았던 일 | 최대 2 |
| 노랑 | 어떤 하루였는지 | 최대 2 |
| 빨강 | 무슨 일이 있었는지 | 최대 2 |
| **남색** | **"조용히 있고 싶구나" + "오늘 하루는 어땠어?"** | **최대 2** |

### 1.5 남색 — 기획안을 바꾼다

기획안 §5.2 는 **남색이면 대화를 시작하지 않는다**고 정했다.

> AI 가 대화를 걸지 않습니다. 혼자 있고 싶다고 한 아이에게 말을 거는 건 모순입니다.
> 아이는 **자기 요청이 받아들여지는 경험**을 하고 …

**그런데 이 설계에는 구멍이 있다.** 남색만 즉시 종료면 **가장 편한 선택지**가 되고,
아이들은 금방 학습한다. 귀찮은 날 남색을 누르면 끝나는 구조다.
그러면 기준선이 오염되고, 정작 진짜 남색인 아이를 구분할 수 없다.

**해결: 질문의 대상을 바꾼다.**

- ✗ "왜 혼자 있고 싶어?" — 요청을 받아들인다면서 이유를 캐묻는 것
- ✓ "알겠어, 오늘은 조용히 있고 싶구나. 그래도 하나만 — **오늘 하루는 어땠어?**"

남색 선택 자체를 캐묻지 않고 **하루에 대해** 묻는다.
다른 색과 품이 같아져 도피처가 되지 않고, 데이터도 남는다.
그 뒤로는 기획안대로 더 캐묻지 않는다.

**보강:** 남색이 며칠 연속이면 그 자체가 교사에게 가장 중요한 신호다.
`/api/ai/pattern-alert`(규칙 기반 집계)가 그 자리다.

### 1.6 가이드 칩

"이런 이야기로 시작해도 좋아요" 칩은 **망설일 때만** 올라온다(3.5초).
상시 노출하면 말하기 버튼과 같은 비중이 되어 주객이 바뀐다.

**칩 내용은 주제여야 한다. 문장이면 안 된다.**

- ✓ `오늘 학교에서 있었던 일` / `지금 기분이 이런 이유` / `선생님이나 친구와 있었던 일`
- ✗ `아침에 엄마랑 싸웠어요` — 아이 상황을 단정하므로 안 맞으면 엉뚱해진다

주제는 단정하지 않으므로 **틀릴 수가 없다.** 색 기반 고정으로 충분하고,
여기에 LLM 호출을 붙일 이유가 없다. **맥락은 유도 질문에만 쓴다** — 거기는
어차피 LLM 을 부르므로 추가 비용이 거의 없다.

### 1.7 면담 신청

**대화가 끝난 뒤에 노출한다.** 대화 중에 두면 "말하기 시작"과 경쟁한다.
`meeting_requests(requested_by='student')` 로 저장한다.

## 2. 감정 추론 — 무엇을 하고 무엇을 하지 않는가

### 2.1 하지 않는 것

**목소리로 감정을 판정하지 않는다.** 이 분야는 학계에서 심하게 논쟁 중이다.

Lisa Feldman Barrett 의 2019년 리뷰:

> 미소에서 행복을, 찌푸림에서 분노를 **확신을 갖고 추론하는 것은 불가능하다.**
> **automated emotion recognition 이라는 것은 없다.**

비판의 핵심은 감정 인식이 **거짓말 탐지기와 같은 전제**에 선다는 것이다 —
"신체 신호가 내면 상태와 안정적으로 대응한다"는 가정이 성립하지 않는다.
실제로 HireVue 는 영상 분석을 중단했고, Microsoft 는 Face API 감정 인식 공개를 중단했다.

### 2.2 하는 것

```
객관 수치   무음 길이 · 발화 속도 · 음량 변화 · 응답 지연   → 신호처리(결정론적)
해석        위축인지 피로인지                              → LLM (수치 + 전사 입력)
표시        "발화 속도가 줄고 말수가 적어졌어요"            → 관찰 기술
판단        교사                                           → 사람
```

**"발화 속도가 줄었다"는 감정 판정이 아니라 측정 결과의 기술이다.**
이 구분이 Barrett 의 비판을 피해 가는 지점이다.

### 2.3 넘으면 안 되는 선

| 안전 | 위험 |
|---|---|
| "발화 속도가 줄고 말수가 적어졌어요" | "불안해 보여요" |
| "3일 연속 빨강을 골랐어요" | "우울 위험 62%" |
| "먼저 말을 꺼내는 날이 늘었어요" | "정서 상태 호전" |
| 본인 기준선 대비 변화 | 또래 비교 · 백분위 |

**이 제약은 프롬프트와 코드에 강제해야 한다.** 문서에만 적어두면 지켜지지 않는다.

`emotion_tags`(위축/피로/흥분) 는 이미 판정에 가깝다.
**교사에게 노출하지 않고 내부 집계용으로만** 쓰거나, 빼는 것을 검토한다.

## 3. 근거 — 왜 이 지표들인가

### 3.1 음향 지표는 임상 연구에서 반복 검증되었다

우리가 뽑는 수치(무음 길이, 발화 속도, 응답 지연)는 임의로 고른 것이 아니다.

- **말속도 감소 + 무음 구간 증가**가 우울 중증도와 일관되게 연관됨
- 우울과 불안이 **다른 패턴**을 보인다 — 우울은 무음이 길고 편차가 큼,
  불안은 무음 비율과 횟수가 증가
- 일부 리뷰에서 정확도 78~96% 보고
- 3~8세 아동 대상 연구도 존재

> **한계:** 이 연구들은 대부분 **임상 코호트 · 통제된 환경**이다.
> 교실에 그대로 옮기면 정확도가 떨어진다. 우리는 진단이 아니라
> **교사가 확인할 단서**를 만드는 것이므로 이 한계를 안고 갈 수 있다.

### 3.2 개인 기준선 방식이 방법론적으로 더 강하다

기획안은 **"본인 평균 대비 −30%"** 로 적었다. 집단 기준이 아니라
**개인 기준선 대비 변화**다. 연구가 정확히 이것을 지지한다.

> 집단 수준 모델은 **개인차 때문에 기분 변동을 잡아내기에 부적합**하다.
> 개인마다 말하는 스타일이 다르고, 특정 음성 지표가 그 개인에게만 유효한 신호일 수 있다.
> 관찰된 차이가 **그 개인에게 의미 있는 변화인지 판단하려면 개인·과제별 기준선이 필요**하다.

집단 비교는 **에르고딕성**(사람들이 비슷하고 시간에 따라 변하지 않는다)을 가정하는데
그것이 성립하지 않는다.

**"이 아이가 어제보다 느려졌다"** 는 **"또래 평균보다 느리다"** 보다 훨씬 방어 가능하다.

### 3.3 한국 아동 데이터 — 개인 기준선이 필수인 이유

외국 연구만으로는 부족하다. 무음·속도 같은 지표는 언어 보편적 측면이 있지만,
**한국어 운율과 한국 아동의 규준은 다르다.** 국내 연구에서 확인되는 것:

- **한국어 발화 속도는 연령에 따라 유의하게 증가한다** (만 3~8세 아동 144명 대상,
  2년 간격으로 통계적으로 유의한 증가)
  → **학년이 다르면 기준이 다르다.** 3학년과 4학년을 같은 잣대로 볼 수 없다
  → 개인 기준선 방식이 선택이 아니라 **필수**임을 뒷받침한다
- **아동은 음성에서 정서를 알아보는 능력 자체가 성인보다 낮다**
  (정상청력 아동 65.79% vs 성인 88.49%)
  → 사람도 66% 수준인 과제다. 기계 추론에 과한 주장을 얹으면 안 된다
- 한국 아동 감정 발화의 음향학적 분석 연구가 국내에 존재한다
- **AI-Hub 아동 음성 데이터**(정부 구축)가 있다 — STT 정확도 개선에 활용 가능

### 3.4 콜드스타트는 선택이 아니다

기획안: *"첫 2주는 지표를 띄우지 않고 '기준선 수집 중 9일 / 14일' 표시"*

개인 기준선 방식에서는 **기준선이 없으면 비교 대상이 없다.**
이 표시는 정직함의 문제가 아니라 **논리적 필연**이다.

### 3.5 대외 설명 문구

> 살핌은 감정을 **판정하지 않습니다.**
> 말속도·무음·응답 지연을 결정론적으로 측정하고,
> **그 아이 본인의 기준선 대비 변화**만 교사에게 제시합니다.
> 이 지표들은 임상 연구에서 정서 상태와의 연관이 반복 확인된 것이며,
> 개인 기준선 방식은 집단 비교보다 개인차에 강합니다.
> **최종 판단은 교사가 합니다.**

## 4. "발화 심리 전문가" 에이전트 컨셉

교사 Agent 는 이미 **분과 전문가 병렬 구조**로 설계되어 있다.

```
협진 챗봇 = 3개 system prompt 병렬 호출 후 합치는 구조
agent_messages.domain = learning | emotion | home
```

**학생 대화에서 나온 데이터도 같은 구조에 얹는다.**

```
아이 발화
  ↓
[발화 심리 전문가]   ← 수치 + 전사를 받아 관찰 기술 1문장 생성
  ↓
analysis_runs 에 저장 (analysis_type = 'emotion')
  ↓
교사 화면
  ├ 아침 브리핑 reason        "발화 속도가 줄고 말수가 적어졌어요"
  └ 협진 챗봇 emotion 도메인   근거 ID 로 참조
```

**이 컨셉의 장점**

- 교사 Agent 의 `domain='emotion'` 과 자연스럽게 연결된다. 없던 구조를 새로 만들지 않는다
- 역할이 좁아져 프롬프트에 **판정 금지 제약을 걸기 쉽다**.
  "너는 관찰 기술만 한다. 진단·점수·감정 단정을 하지 않는다"
- 교사에게 설명하기 쉽다 — *"발화를 보는 전문가가 관찰한 내용"*

**주의할 것**

- "전문가"라는 말이 **임상 전문가로 오해**되면 안 된다.
  대외 문구에서는 *"발화 관찰"* 처럼 판정 뉘앙스가 없는 표현을 쓴다
- 전문가가 늘어도 **판정 금지선은 모두에게 동일**하게 적용한다

## 5. 스키마 — 대부분 이미 있다

> **정정(2026-09-18):** 이 문서 초안에는 "analysis 테이블이 없다"고 적혀 있었다. **틀렸다.**
> 조사해 보니 기획안 §8.3 이 요구한 구조가 이미 구현되어 있다.

### 5.1 `analysis_runs` — 이미 있다

```sql
analysis_runs
  analysis_type      'emotion' | 'relationship' | ...   ← 발화 심리 전문가는 여기
  source_type        'session'                          ← 세션 단위 추론(§8.2)
  source_id          checkin_sessions.id
  provider, model, prompt_version, schema_version       ← "해석은 버전" 구현체
  category_tags[]                                       ← emotion_tags 자리
  moderation_flag                                       ← 위험 신호 하드 게이트
  needs_followup                                        ← 교사 확인 필요
  result jsonb                                          ← 해석 본문
  status, error_message                                 ← 실패 처리
```

기획안 §8.3 의 **"원본은 불변, 해석은 버전"** 이 `prompt_version` · `schema_version` 으로
이미 구현되어 있다. 새로 만들 것이 없다.

### 5.2 교사 화면 연결도 이미 있다

```sql
v_signal_flags   -- analysis_runs → checkin_sessions → enrollments
  where status = 'completed'
    and (moderation_flag or needs_followup or analysis_type = 'relationship')
```

`moderation_flag` 나 `needs_followup` 을 켜면 **자동으로 교사 뷰에 올라온다.**
`get_student_context()` 도 이 뷰를 읽는다. 위험 신호 게이트(§1.3)의 출력 경로가 이미 뚫려 있다.

### 5.3 없었던 것 — `prosody` 하나

발화 파생 수치를 저장할 자리가 없었다. 기획안 §8.1 이 저장하라고 한 값이다.

```
전사 텍스트          → 저장
파생 수치 (prosody)  → 저장   ← 자리가 없었다
원본 음성            → 즉시 파기
```

이 수치가 없으면 교사 화면의 **"검증 가능한 근거"** 가 나오지 않는다.
`analysis_runs.result` 에 해석을 남겨도, 그 해석의 근거가 되는 측정값은
원본 쪽에 있어야 "원본은 불변, 해석은 버전"이 성립한다.

**`20260918100000_1080_session_prosody.sql`** 로 추가했다.
순수 추가·nullable 이라 기존 읽기(강윤지님 아이템 파이프라인 포함)에 영향이 없다.

```
checkin_sessions.prosody jsonb
{
  "utterances": [
    { "index": 0,
      "duration_sec": 12.4,
      "response_delay_sec": 3.1,
      "silence_count": 2,
      "silence_total_sec": 3.1,
      "syllables_per_sec": 2.1,
      "loudness_rel": -0.30 }      -- 본인 평균 대비
  ],
  "baseline_days": 14              -- 부족하면 해석하지 않는다
}
```

`baseline_days` 를 같이 저장하는 이유: 개인 기준선 방식에서는 **기준선이 없으면 비교가 성립하지 않는다**(§3.4).
나중에 "이 해석이 며칠 치 기준선 위에서 나온 것인지" 를 되짚을 수 있어야 한다.

### 5.4 `analysis_runs.result` 구조 (우리가 정하는 계약)

스키마 변경이 아니라 jsonb 내부 규약이므로 코드에서 정한다.

```json
{
  "summary_for_teacher": "발화 속도가 줄고 말수가 적어졌어요",
  "evidence": "발화 2.1→1.4음절/초, 무음 3회, 본인 평균 대비 -30%",
  "baseline_days": 14
}
```

`summary_for_teacher` 가 아침 브리핑의 `reason` 으로 그대로 들어간다(§4).
**감정 단정 문장을 여기 넣으면 안 된다**(§2.3).

## 6. 팀 확인이 필요한 것

> 초안에 있던 "테이블 추가" 항목은 **이미 있는 것으로 확인되어 삭제**했다(§5).

1. **남색 처리 변경** — 기획안 §5.2 를 바꾸는 결정 (§1.5)
2. **AI 벤더** — 기획안은 대화에 Claude, 아이템 파이프라인은 OpenAI 를 쓴다
3. **전문 저장과 아이템 작업 접수를 한 API 로 묶을지** — 아래 §7
4. **`category_tags` 를 교사에게 노출할지** — 판정에 가까운 값이다 (§2.3)
5. **위험 신호 처리의 전문가 검토** — 상담 교사·법률. 아동학대 신고 의무와 연결된다
6. **STT 학습 사용 opt-out 확인** — 기획안 §8.1: *"이게 없으면 '저장하지 않습니다'가 반쪽"*

## 7. 강윤지님 작업과의 경계

```
[이유민]  대화 → 전문 저장 → 작업 접수(queued)
──────────────────── 경계 ────────────────────
[강윤지]  작업 실행기 → 소재 추론 → 조립 → 지급 → 교체
```

넘기는 것은 **`session_id` 하나**다. 전문은 DB 에 있으므로 강윤지님이 직접 읽는다.

### 7.1 지켜야 할 규약

**전문 형식** — 이 형식만 통과한다(`parseTranscript`).

```ts
{ speaker: "student" | "assistant" | "system",
  content: string,                      // 빈 문자열 불가
  input_method: "voice" | "text" | "fixed" }
```

고정 첫 질문은 `"fixed"`, 음성 발화는 `"voice"`.

**저장은 딱 한 번** — `saveWholeTranscript()` 는 `transcript IS NULL` 일 때만 쓴다.
대화 중 부분 저장은 불가능하고, 끝에 통째로 한 번이다.
동일 내용 재시도는 안전하지만 **다른 내용의 두 번째 저장은 거부**된다.

### 7.2 결정이 필요한 지점 — 작업 접수

> 상담 종료 요청과 작업 접수는 **멱등적이어야 한다.** 같은 `source_session_id` 로
> 두 번 요청해도 작업과 지급이 하나만 생겨야 한다. — `item-generation-jobs.md`

| 방식 | 장점 | 단점 |
|---|---|---|
| A. 이유민이 저장 후 접수를 따로 호출 | 경계가 명확 | 중간 실패 시 전문만 남고 작업이 없다 |
| **B. 저장 API 가 저장+접수를 함께** | **원자적, 누락 없음** | 저장 함수가 아이템을 알게 된다 |
| C. DB 트리거 | 코드 없음 | 디버깅 어려움 |

**B 를 권한다.** `item_generation_jobs.source_session_id` 가 **UNIQUE** 라
중복 접수가 DB 에서 막힌다. 저장과 접수가 한 번에 일어나면
"전문은 있는데 아이템이 없는" 상태가 원천적으로 생기지 않는다.

### 7.3 이유민 작업에 영향이 없는 부분

`item_generation_jobs` 에 `queued` 행을 만드는 것까지가 이유민 몫이다.
그 뒤(작업 실행기, 같은 자리 교체)는 강윤지님 영역이고, 늦어져도 이쪽 작업은 완결된다.

다만 **타임아웃 주의**: 소재 45초 + 조립 60초라 **대화 종료 요청에 직렬로 붙이면 상한을 넘는다.**
반드시 작업으로 분리한다.
