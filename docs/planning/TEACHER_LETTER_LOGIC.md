# 등교 홈 선생님 편지 — 표시 로직

> 작성: 2026-09-16 · STU-001-B (Claude 세션)
> 근거: `docs/planning/살핌_DB_스키마_v0.3.md` §8 교사 피드백

## 무엇을 보여주는가

`feedback_drafts` 테이블이 이미 이 용도로 설계되어 있다.

| 컬럼 | 학생 화면에서 |
|---|---|
| `draft_text` | **절대 노출 금지.** 교사 검토 전 AI 초안이다 |
| `final_text` | **이것만 보여준다.** 교사가 검토·수정한 실제 발송문 |
| `status` | `'sent'` 인 것만 조회 (스키마 문서에 명시) |
| `sent_at` | 최신 것을 고르는 기준 |

스키마에 `check ((status = 'sent' and sent_at is not null and final_text is not null) or ...)` 제약이
걸려 있어, `status = 'sent'` 면 `final_text` 와 `sent_at` 이 반드시 존재한다. 널 체크가 불필요하다.

인덱스도 이미 있다: `feedback_drafts_enrollment_status_idx (enrollment_id, status, created_at desc)`

## 운영 방식 확정 (2026-09-16 유민님 결정)

**교사가 하교 후 퇴근 전에, 반 전원에게 짧은 코멘트를 매일 남긴다. 초안은 AI 가 만든다.**

이 결정은 기획안이 짚은 문제와 정확히 맞물린다.

> "보통의 예쁜 평범한 아이들의 감정을 더 살펴주지 못하고 에너지 써주지 못하는 **죄책감**이
> 대부분의 선생님들이 굉장히 큼. 금쪽이에게 에너지를 다 뺏겨서 우리 반 유니콘에게
> 긍정적인 피드백을 주지 못하는데." — 교사 인터뷰 2026-09-12

> "기록하고 교사가 클릭? AI 이용해서 짧게 빠르고 간단하게 긍정 피드백 줄 수 있으면
> 이 부분도 좀 해결될 것 같음"

기획안 §교사 부담 표에도 **"손댓글 28개 → 원터치"** 로 명시되어 있다.

### 여기서 따라오는 것

**전원 매일**이므로 "편지 없는 날"은 예외가 된다(교사 결근, 방학, 주말 다음날).
편지 없을 때 인사 화면으로 분기하는 처리는 그대로 유지한다 — 예외가 없어지진 않는다.

**"원터치"가 핵심이다.** 28명분을 한 명씩 고쳐 쓰는 게 아니라,
AI 초안 목록을 보고 대부분 그대로 승인하고 몇 개만 손보는 흐름이어야 한다.

> 구현 주의: 스키마에 `status='sent'` 이면 `final_text` 가 반드시 있어야 한다는 제약이 있다.
> 교사가 초안을 **그대로 승인**해도 `final_text := draft_text` 로 복사해 넣어야 한다.
> 일괄 승인 쿼리를 짤 때 빠뜨리기 쉬운 지점이다.

## 언제 보여주는가 — 정해야 할 것

**핵심 질문: 한 번 본 편지를 다음 날에도 또 보여줄 것인가?**

세 가지 선택지가 있고, 각각 다른 것을 얻는다.

| 방식 | 조회 조건 | 장점 | 단점 |
|---|---|---|---|
| **A. 최신 1건** | `status='sent'` 중 `sent_at` 최신 1건 | 구현 가장 단순. 추가 테이블 없음 | 이미 읽은 편지를 며칠이고 다시 본다 |
| **B. 오늘 발송분만** | 위 + `sent_at::date = 오늘` | "오늘의 편지" 의미가 명확 | 어제 보낸 편지를 아이가 결석해서 못 보면 영영 못 봄 |
| **C. 안 읽은 것** | 위 + 읽음 기록에 없는 것 | 아이가 반드시 한 번은 본다 | **읽음 상태를 저장할 곳이 필요** |

### 권장: C — 단, 읽음 컬럼 없이 구현할 수 있다

**매일 전원에게 보내기로 했으므로 A(최신 1건)는 쓰면 안 된다.**
교사가 하루 건너뛰면 어제 편지가 그대로 다시 떠서, 아이가 같은 글을 이틀 연속 본다.

그런데 **읽음 기록 컬럼을 새로 만들 필요가 없다.**
학생이 등교 홈을 보는 시점이 곧 등교 체크인이므로, `checkin_sessions` 가 이미 읽음 표식 역할을 한다.

```sql
select fd.id, fd.final_text, fd.sent_at
from feedback_drafts fd
where fd.enrollment_id = $1
  and fd.status = 'sent'
  and fd.sent_at > coalesce(
    (select max(cs.started_at)
       from checkin_sessions cs
      where cs.enrollment_id = $1
        and cs.period = 'morning'),
    '-infinity'::timestamptz)
order by fd.sent_at desc
limit 1;
```

교사가 하교 후에 보내므로, 다음 날 등교 때 `sent_at` 이 마지막 등교 시각보다 뒤가 되어 편지가 뜬다.
같은 날 두 번 열면 이미 세션이 있으므로 다시 뜨지 않는다.

> **선행 조건:** `checkin_sessions` 행이 **언제 만들어지는가**에 이 로직이 달려 있다.
> 홈 화면(1단계)에서 만들면 자기 세션 때문에 편지가 즉시 사라진다.
> **색 선택(2단계)에서 만들어야 한다.** 아직 세션 생성이 구현되지 않았으므로 지금 정해두면 된다.

이 방식이 안 맞으면 대안은 `feedback_drafts.read_at` 컬럼 추가인데,
`sent` 이후 수정 금지 규칙과 충돌하는지 팀 확인이 필요하다.

## 편지가 없을 때 — 이게 기본값이다

**교사가 매일 모든 학생에게 편지를 쓰지는 않는다.** 편지가 없는 날이 오히려 일반적이다.

- 편지 없음 → 등교 홈은 **편지를 닫았을 때와 같은 인사 화면**으로 시작한다
  (좋은 아침이야, 민준아! / 오늘도 네 마음을 들려줘!)
- 이미 그 화면이 구현되어 있으므로 분기만 하면 된다
- 빈 편지 봉투나 "오늘은 편지가 없어요" 같은 안내는 **넣지 않는다.**
  아이에게 "나는 편지를 못 받았다"는 인상을 주기 때문이다

## 길이 — 스크롤로 흡수한다 (2026-09-16 결정)

**글자 수 제한은 두지 않는다.** 교사가 길게 쓰면 편지 본문만 스크롤된다.

- 스크롤되는 건 **본문뿐**이다. 머리말(선생님 이름·해 아이콘)과 서명은 고정
- 본문 최대 높이 `33cqh`. 넘치면 얇은 스크롤바가 생긴다
- 구현: `.sh-letter-scroll` (`src/styles/student-home.css`)

> 다만 아이가 스크롤해야 읽히는 편지는 기획안의 "30초" 흐름과 어긋난다.
> 운영하면서 실제로 길게 쓰는 교사가 많으면, 그때 AI 초안 프롬프트에
> 길이 가이드를 넣는 쪽으로 다시 볼 것.

## 교사 이름과 사진 (2026-09-16 조사)

### 이름 — 스키마에 이미 있다. 추가 작업 없음

`profiles(id, role, display_name)` 에 `display_name` 이 있다.
다만 **`feedback_drafts` 는 누가 썼는지 기록하지 않는다** (`enrollment_id`, `created_by='ai'|'teacher'` 뿐).

MVP 에서는 **담임을 조회해서 쓰면 된다.**

```sql
select p.display_name
from enrollments e
join class_teachers ct on ct.class_id = e.class_id and ct.role = 'homeroom'
join profiles p on p.id = ct.teacher_id
where e.id = $1;
```

> 한계: 보조교사·상담교사도 편지를 보낼 수 있게 되면 담임 이름이 잘못 표시된다.
> 그때는 `feedback_drafts.sent_by uuid references profiles(id)` 를 추가해야 한다.
> **지금 추가해 두는 편이 낫다** — 나중에 넣으면 과거 데이터의 작성자를 복원할 수 없다.

### 사진 — 컬럼이 없다. MVP 는 넣지 말 것을 권한다

`profiles` 에 아바타 컬럼이 없다. 넣으려면 컬럼 + Storage 버킷 + 업로드 화면이 모두 필요하다.

**MVP 에서는 사진 없이 가는 것을 권한다.** 이유 셋.

1. **업로드 흐름이 통째로 필요하다** — 교사 설정 화면, 이미지 크롭, 용량 제한
2. **교사 사진도 개인정보다.** 학생 사진만큼은 아니어도 동의 절차가 필요하다
3. **아이에게 주는 가치가 작다.** 이름과 말투로 이미 "우리 선생님"이 전달된다

대신 **빈 원형 대신 브랜드 색 원에 이름 첫 글자**를 넣으면 허전하지 않다.
살핌 로고의 웃는 얼굴을 재사용하는 방법도 있다.

나중에 넣는다면:

| 항목 | 방식 |
|---|---|
| 컬럼 | `profiles.avatar_url text` |
| 저장 | Supabase Storage 공개 버킷 (학생 자료와 달리 signed URL 불필요) |
| 주의 | 교사 동의, 퇴직 시 삭제 절차 |

## 지금 코드 상태

`src/lib/types/letter.ts` 에 데이터 계약을 정의해 두었다.
`StudentHome` 은 `letter` prop 을 받고, 없으면 인사 화면으로 분기하도록 되어 있다.

실제 조회(A 방식) 쿼리는 다음과 같다. API 연결 시 사용한다.

```sql
select id, final_text, sent_at
from feedback_drafts
where enrollment_id = $1
  and status = 'sent'
order by sent_at desc
limit 1;
```

## 팀 확인이 필요한 것

1. **`checkin_sessions` 행을 언제 만들 것인가** — 색 선택(2단계)이어야 읽음 판정이 성립한다.
   홈 화면(1단계)에서 만들면 편지가 뜨자마자 사라진다. **가장 먼저 정해야 할 것**
2. **`feedback_drafts.sent_by` 컬럼을 지금 추가할지** — 나중에 넣으면 과거 작성자 복원 불가
3. **일괄 승인 시 `final_text := draft_text` 복사** — 스키마 제약상 필수
